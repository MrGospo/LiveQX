# LiveQX

**LiveQX** — это C++ движок, предназначенный для непрерывного вещания медиаконтента: он воспроизводит плейлисты, включающие фото‑ и видеофайлы. Функционал каждого канала приближен к полноценному телеканалу: через веб‑интерфейс оператор формирует плейлист, а движок автоматически обрабатывает материалы — считывает их с локального накопителя либо из сетевой папки (CIFS/SMB), выравнивает уровень звука, соединяет фрагменты с применением различных переходов (cross‑fade, dissolve, fade‑to‑black, push, wipe) и транслирует поток в формате MPEG‑TS сразу по нескольким протоколам: SRT, HLS, RTMP, RTSP и multicast UDP — то есть обеспечивает параллельную выдачу на разные выходы с одного канала.

При наличии GPU можно задействовать аппаратное кодирование — NVENC, QSV или VAAPI. В базовой комплектации предусмотрены: разграничение прав доступа по модели RBAC с настройкой разрешений для каждого канала, возможность интеграции с LDAP, сбор метрик для Prometheus, а также предварительный просмотр потока в браузере с минимальной задержкой через WebRTC.

## Архитектура системы LiveQX

### Ядро обработки видео

В основе работы движка — кадровый цикл (frame‑based render loop): для каждого канала выделяется собственный поток, который генерирует кадры с фиксированным временным шагом вдоль таймлайна.

Для унификации работы с медиаконтентом используется единый интерфейс `IClip`, поддерживающий три типа клипов:

- **ImageClip** — фотоматериалы, длительность которых задаётся в интерфейсе, а кадр помещается в кэш;
- **VideoClip** — видео, длительность которого определяется данными контейнера; воспроизведение всегда завершается корректно, до конца файла;
- **FallbackClip** — заглушка, которая активируется, если плейлист пуст либо источник недоступен.

Переходы между фрагментами и компоновка изображения реализуются через подключаемые интерфейсы `ITransition` и `ICompositor`. По умолчанию применяется кроссфейд (cross‑fade).

Выбор кодировщика осуществляется с помощью фабрики: базовым вариантом выступает x264 (на базе CPU) — он доступен всегда. При необходимости можно задействовать аппаратное кодирование: NVIDIA NVENC, Intel Quick Sync (QSV) или VAAPI (для Linux, GPU от AMD и Intel). Активация этих модулей производится на этапе сборки через CMake‑флаги `ENABLE_NVENC`, `ENABLE_QSV` и `ENABLE_VAAPI`.

Межпоточная передача данных организована с использованием lock‑free очередей типа SPSC между этапами чтения, декодирования, кодирования и вывода. Для оптимизации памяти применяется пул кадров (FramePool), что позволяет избежать динамического выделения памяти в «горячих» участках кода.

Стандартный выходной профиль — 720p при 25 кадрах в секунду, кодеки H.264 и AAC, контейнер MPEG‑TS. При этом параметры кодирования можно гибко настраивать отдельно для каждого канала.

### Управление каналами и конфигурацией

Для каждого канала предусмотрена собственная директория с чёткой структурой: `channels/ch{id}-{name}/`, внутри которой размещаются `config.json`, папки для логов (`logs/`), кэша (`cache/`) и воспроизведения (`playback/`). Файл `config.json` выступает единственным достоверным источником настроек канала. Обновление конфигурации реализовано атомарно: изменения сначала пишутся во временный файл, затем происходит переименование и принудительная синхронизация на диск (`fsync`).

При запуске системы `ChannelManager` сканирует все папки `channels/*/config.json`. При этом ошибка в конфигурации одного канала не влияет на работу остальных.

Глобальный файл `config.json` содержит только настройки уровня процесса: параметры API и TLS, уровень логирования, корневой каталог дерева каналов, настройки watchdog‑механизма.

### Разрешение путей

Класс `Paths` формирует пути (`state_dir`, `log_dir`, `channels_dir` и др.) согласно приоритету источников: флаги командной строки > переменные окружения > конфигурационный файл > значения по умолчанию.

По умолчанию система ориентируется на стандарт FHS: если существует директория `/var/lib/liveqx`, она будет использована. В противном случае применяются пути относительно текущей рабочей директории — это удобно для разработки и тестирования.

### Источники медиаконтента

Контент может располагаться в локальной папке либо в сетевой шаре (CIFS/SMB).

Для отслеживания изменений в директориях задействован фоновый механизм (`ShareScanner` + `ContentSync`): он индексирует содержимое, реагирует на появление или удаление файлов и автоматически обновляет плейлист.

Поддерживается динамическое подключение сетевых ресурсов без перезапуска движка. Для этого используется отдельный systemd‑юнит `liveqx-mountd`, запускаемый от имени root и выполняющий `mount.cifs`. Основной процесс получает уведомление об изменениях через механизм распространения событий в mount‑namespace.

### Выходы и трансляция

Система позволяет одновременно отдавать поток с одного канала по нескольким протоколам: SRT, HLS, RTMP, RTSP и multicast UDP. При этом используется один кодировщик, а ветвление пакетов реализуется на уровне packetizer’а. `OutputManager` отвечает за мультиплексирование и распределение потока по набору транспортных протоколов.

Для предпросмотра в интерфейсе предусмотрен WebRTC‑поток (на базе libdatachannel) с низкой задержкой: разрешение 480p, сигнал берётся с tap‑интерфейса на рендер‑потоке. Это даёт возможность просматривать канал в UI без выхода в основной эфир.

### API и пользовательский интерфейс

Управление системой осуществляется через HTTP/HTTPS Control API на базе cpp‑httplib. При первом запуске автоматически генерируются CA‑сертификат и самоподписанный сертификат. Поддерживаются разные режимы работы: `auto`, `provided`, `behind_proxy`, `disabled`.

Web‑интерфейс реализован на React и подключается через параметр `--ui-dir`. Предусмотрен SPA‑фолбэк для корректной работы react‑router. Внутри UI размещена двуязычная база знаний (русский и английский).

Для оперативного обновления статусов используется SSE‑поток событий.

Метрики собираются в формате, совместимом с Prometheus, по эндпоинту `/api/metrics`. Доступ защищён bearer‑токеном, который генерируется при первом старте и хранится в `state_dir`.

### Безопасность

Аутентификация локальных пользователей реализована на базе bcrypt, сессии передаются через JWT.

Модель контроля доступа (RBAC) предусматривает три роли: `admin`, `operator`, `viewer`, с возможностью назначения прав на уровне отдельных каналов. Эндпоинт `/api/status` автоматически фильтрует данные в соответствии с выданными грантами.

Опционально поддерживается интеграция с LDAP.

Мастер‑ключ (на базе libsodium) хранится либо в файле `state/master.key` (с правами `0600`), либо в переменной окружения `LIVEQX_MASTER_KEY` (в формате base64). Сброс ключа выполняется через CLI с эксклюзивной блокировкой, созданием резервной копии и очисткой учётных данных для LDAP, SMTP и сетевых шар.

### Работа со временем

Система включает встроенный SNTP‑клиент и учитывает часовой пояс сервера. Для каждого канала можно задать собственный часовой пояс — по умолчанию он наследуется от системной настройки. Временные метки кадров (render‑таймстампы) монотонны, а расписание воспроизведения плейлистов привязано к локальному времени канала.

### Хранение данных и устойчивость

Для хранения данных используется SQLite:

- `auth.db` — учётные записи пользователей, роли и токены;
- `mounts.db` — учётные данные для CIFS‑шар, зашифрованные мастер‑ключом;
- `playback.db` (отдельно для каждого канала) — данные о воспроизведении, разбитые по ISO‑неделям (например, `2026-W22.db`), с настройкой срока хранения и статусами (`completed`, `skipped_user`, `removed`, `error`).

Миграции схемы БД выполняются через `PRAGMA user_version`. Если версия базы данных выше версии исполняемого файла, система откажется запускаться — это предотвращает незаметное повреждение данных.

### Обработка аудио

Декодирование аудио производится средствами FFmpeg, нормализация выполняется по стандарту EBU R128 до целевого уровня −23 LUFS. Аудио кодируется в AAC (стерео, 48 кГц, 128 кбит/с). Для `ImageClip` генерируются кадры тишины.

На стыках клипов применяется плавный переход звука (audio crossfade): затухание предыдущего фрагмента и нарастание следующего. Синхронизация аудио и видео осуществляется по PTS в мультиплексоре.

### Защитные механизмы и отказоустойчивость

Чтобы избежать появления чёрного экрана при сбоях декодера, система сохраняет последний удачный кадр (`last_good_frame`) и повторяет его при просадке производительности.

Метод `getFrame()` реализован как неблокирующий, с таймаутом: при задержке используется `last_good_frame`, благодаря чему рендер‑цикл не останавливается из‑за операций ввода‑вывода.

Механизм `Preloader` заранее подготавливает следующий клип за N секунд до перехода; на производительном оборудовании значение N можно увеличить.

`FallbackClip` обеспечивает непрерывность потока: при отсутствии контента или недоступности папки воспроизводится статичная заглушка с тишиной. Таким образом, трансляция не прерывается ни при каких обстоятельствах.

Интеграция с systemd реализована через watchdog и `sd_notify`: если рендер‑цикл зависает, срабатывает watchdog, и система перезапускается.

## Control API

HTTP/JSON REST поверх cpp‑httplib. Полная спецификация — в `openapi.yaml` в корне репозитория. Основные группы эндпоинтов:

| Группа       | Префикс                                     | Что делает                                     |
|--------------|---------------------------------------------|------------------------------------------------|
| Каналы       | `/api/channels`                             | CRUD каналов, статус, конфиг                   |
| Плейлист     | `/api/channels/{id}/playlist`               | Загрузка, append, удаление, notify‑deleted     |
| Транспорт    | `/api/channels/{id}/{play,stop,next}`       | Запуск, остановка, принудительный skip         |
| Мониторинг   | `/api/health`, `/api/metrics`               | Health‑check, Prometheus‑метрики               |
| Системные    | `/api/system/{interfaces,time,…}`           | NIC, NTP, server timezone                      |
| Auth/RBAC    | `/api/auth`, `/api/users`, `/api/sessions`  | Логин, JWT, пользователи, гранты               |
| Mounts       | `/api/mounts`                               | CIFS‑шары: добавление, обновление, статус      |
| TLS          | `/api/tls/*`                                | Сертификаты, CA, регенерация                   |
| Превью       | `/api/preview/*`                            | WebRTC offer/answer                            |
| Stress       | `/api/stress/*`                             | Нагрузочные сценарии и отчёты                  |

OpenAPI‑контракт в файле `openapi.yaml` выступает единственным достоверным источником схем запросов и ответов. На его основе автоматически формируются TypeScript‑типы для фронтенда — для этого запускается команда `npm run gen:api-types`. Кроме того, контрактные тесты, размещённые в директории `tests/`, используют этот файл как эталон: они проверяют, соответствуют ли реальные ответы движка описанным в контракте схемам.

### Пример конфига канала

`channels/ch1-news/config.json`:

```json
{
  "id": 1,
  "name": "News",
  "resolution": "1280x720",
  "fps": 25,
  "bitrate": 4000000,
  "preset": "medium",
  "scale_mode": "fit",
  "default_photo_duration": 10.0,
  "default_transition": { "type": "crossfade", "duration": 2.0 },
  "fallback": { "image_path": "/var/lib/liveqx/fallback.png" },
  "outputs": [
    { "type": "srt",  "port": 9000, "latency_ms": 200 },
    { "type": "rtmp", "url": "rtmp://server/live/ch1" }
  ],
  "audio": {
    "codec": "aac", "bitrate": 128000, "sample_rate": 48000,
    "normalize": true, "target_lufs": -23
  }
}
```

Обновление конфигурации канала выполняется через `PATCH`‑запрос (или `PUT`) по адресу `/api/channels/{id}/config`. Операция реализована как атомарная перезапись: данные сначала записываются во временный файл, затем файл переименовывается и синхронизируется с диском (через `fsync`). При этом перезапуск канала не требуется — изменения применяются «на лету».

## Установка LiveQX

Система совместима с Ubuntu 22.04 и новее (включая 24.04), а также с Debian 12 и выше. В процессе установки скрипты автоматически:

- устанавливают необходимые зависимости через `apt`;
- создают системного пользователя `liveqx`;
- формируют требуемые директории: `/var/lib/liveqx`, `/etc/liveqx`, `/usr/share/liveqx/ui`, `/mnt/liveqx`;
- размещают три systemd‑юнита: `liveqx-mount-init`, `liveqx-mountd`, `liveqx`;
- запускают основной сервис.

### Вариант 1: установка «с нуля» (сборка и развёртывание одним скриптом)

```bash
git clone https://github.com/MrGospo/LiveQX.git
cd LiveQX
sudo ./packaging/bootstrap.sh
```

Скрипт самостоятельно установит инструменты для сборки (CMake, `build-essential`, Node.js версии не ниже 20, необходимые dev‑пакеты), соберёт бэкенд и веб‑интерфейс, а затем передаст управление скрипту `install.sh`. Чтобы избежать запросов на подтверждение действий, добавьте флаг `-y`:

```bash
sudo ./packaging/bootstrap.sh -y
```

### Вариант 2: развёртывание уже собранного решения

#### Сборка

Выполните следующие команды для компиляции проекта с нужными опциями:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Release \
    -DENABLE_NVENC=ON -DENABLE_QSV=ON -DENABLE_VAAPI=ON \
    -DENABLE_WEBRTC_PREVIEW=ON -DENABLE_SYSTEMD=ON
cmake --build build -j$(nproc) --target liveqx liveqx-mountd
```

Затем соберите пользовательский интерфейс:

```bash
(cd ui && npm ci && npm run build)
```

#### Установка

Запустите скрипт установки:

```bash
sudo ./packaging/install.sh
```

Во время установки система уточнит, какие аппаратные энкодеры (NVENC, VAAPI, QSV) вы планируете использовать. Это действие лишь фиксирует ваш выбор в конфигурации — сами драйверы и SDK (например, компоненты NVIDIA, `intel-media-va-driver`, `libmfx`) нужно установить вручную. После их развёртывания перезапустите сервис:

```bash
sudo systemctl restart liveqx
```

### Проверка и удаление

Для проверки корректности установки используйте:

```bash
sudo ./packaging/install.sh check
```

Эта команда отобразит статус systemd‑юнитов, проверит наличие ключевых файлов и выполнит запрос к эндпоинту `/api/health`.

Чтобы полностью удалить систему, выполните:

```bash
sudo ./packaging/install.sh uninstall
```

Команда удалит бинарные файлы, базы данных, конфигурационные файлы и системного пользователя. Обратите внимание: установленные через `apt` пакеты не будут удалены. При необходимости очистите их вручную:

```bash
sudo apt-get autoremove --purge
```

### Запуск из исходников в режиме разработки

Для отладки и тестирования соберите проект в режиме `Debug`:

```bash
cmake -S . -B build -DCMAKE_BUILD_TYPE=Debug
cmake --build build -j$(nproc)
```

Запустите тесты:

```bash
ctest --test-dir build --output-on-failure
```

И запустите сам движок с конфигурацией по умолчанию:

```bash
./build/liveqx --config config/default.json
```
